# 分布式微服务架构规范

面向 Spring Cloud Alibaba 的服务设计约束。用于方案设计、评审与排障；编码细节见编码规约与脚手架模板。

## 使用方式

设计任何跨服务方案前，先回答：

1. 数据归属哪个服务？
2. 调用是同步还是异步？失败如何补偿？
3. 是否幂等？重复请求会发生什么？
4. 超时预算多少？超时后上游如何处理？
5. 如何观测与定位？

## 一、服务拆分与边界

- 按业务能力（限界上下文）拆分，不按技术层拆分。
- 每个服务独占其数据存储；禁止两个服务直接读写同一张业务表。
- 跨服务通过版本化接口契约或消息交互，不共享数据库、不共享内部实体。
- 同步调用用于需要即时结果的场景；可延迟的一致性动作优先异步。

反例：

```text
订单服务直接 update stock 表
库存服务直接 join 订单表
```

正例：

```text
订单服务 --(下单事件)--> 库存服务扣减库存
订单服务 --(同步查询)--> 库存服务查询可用量
```

契约要求：

- 新增字段保持向后兼容；删除或改语义必须升级版本。
- 对外 DTO 与内部 DO 分离，不暴露存储结构。

## 二、注册发现与配置中心

- 服务通过 Nacos 注册与发现，使用服务名调用，禁止硬编码 IP 与端口。
- 环境、租户通过 namespace / group 隔离，测试与生产不共用配置。
- 敏感配置外置到环境变量或密钥管理，不提交仓库。
- 明确热更新边界：数据源、线程池、连接池等不支持热更新的配置变更需重启。

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR}
        namespace: ${NACOS_NAMESPACE}
      config:
        server-addr: ${NACOS_ADDR}
        namespace: ${NACOS_NAMESPACE}
        group: ORDER_GROUP
```

配置检查：

- [ ] 是否有硬编码地址
- [ ] 是否有明文口令入库
- [ ] 测试与生产是否隔离
- [ ] 哪些配置可热更新，是否写明

## 三、网关职责

- 所有外部流量经统一网关进入。
- 网关负责鉴权、路由、入口限流、协议转换与请求头透传。
- 禁止在网关编写业务逻辑或访问业务数据库。
- 下游服务信任网关透传的身份，避免重复解析原始凭证。

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
          filters:
            - StripPrefix=2
```

透传要求：

- 用户身份（用户 ID、租户 ID、角色）
- traceId
- 调用来源与版本标签（用于灰度）

## 四、超时与容错

- 每次远程调用必须设置连接超时与读取超时。
- 超时预算从入口开始分配，下游总超时不得超过上游剩余预算。
- 熔断、限流、降级规则通过 Sentinel 显式配置，不依赖默认值。
- 重试仅用于幂等操作，且限制次数与退避；非幂等写操作禁止自动重试。
- 降级必须有明确语义：返回缓存、返回兜底值、快速失败，三者选一并说明。

```text
入口 1000ms
├─ 鉴权 50ms
├─ 订单查询 300ms
│  ├─ 库存查询 150ms
│  └─ 用户查询 100ms
└─ 预留 200ms
```

Sentinel 规则示例（思路）：

- 查询接口：QPS 限流 + 慢调用比例熔断
- 写接口：线程数隔离，避免慢调用拖垮整个服务
- 依赖服务不可用时：快速失败并返回明确错误码

## 五、分布式事务与一致性

优先级：最终一致性 > 强一致。选择顺序：

1. 本地事务 + 本地消息表 / 事务消息 + 幂等消费
2. Saga / 补偿事务
3. TCC
4. Seata AT（仅在业务必须强一致且能接受其约束时）

使用 Seata 前必须说明：

- 为什么不能用最终一致性
- 参与者范围与分支事务
- 回滚失败与悬挂事务的处理
- 对性能与锁的影响

最终一致性方案必须包含：

- 消息可靠投递（事务消息或本地消息表）
- 消费幂等
- 不一致检测（对账任务）
- 人工或自动补偿入口
- 监控与告警

反例：

```text
订单库与库存库放在同一个本地事务里
```

正例：

```text
订单本地事务：写订单 + 写本地消息表
投递：定时任务或事务消息发送"下单成功"
库存消费：按订单号幂等扣减
对账：比对订单与库存流水，补偿异常
```

## 六、幂等设计

所有写接口与消息消费者都必须有幂等策略，三选一：

| 策略 | 适用 | 要点 |
| --- | --- | --- |
| 业务唯一键 | 天然唯一，如订单号 | 唯一索引兜底 |
| 幂等令牌 | 客户端重试场景 | 令牌生成、存储、过期 |
| 去重表 | 回调、消息消费 | 唯一键 + 处理状态 |

要求：

- 说明存储位置、唯一约束与过期策略。
- 重复请求返回既有结果，不重复产生副作用。
- 状态机保证非法重复流转被拒绝。

```text
支付回调：以支付流水号作为唯一键插入去重表
- 插入成功：处理业务
- 唯一键冲突：查询并返回既有结果
```

## 七、分布式锁

- 明确实现：Redis 或 ZooKeeper。
- 明确锁粒度：订单级、用户级还是全局。
- 锁必须携带持有者标识，释放时校验，避免误删他人锁。
- 设置租约时间；长任务需要续期（watchdog）或改用状态机。
- 锁内禁止长耗时远程调用。

```java
String token = UUID.randomUUID().toString();
boolean locked = redisLock.tryLock(key, token, Duration.ofSeconds(10));
if (!locked) {
    throw new BusinessException(ErrorCode.CONCURRENT_CONFLICT);
}
try {
    doShortWork();
} finally {
    redisLock.unlock(key, token); // Lua 校验持有者
}
```

评审关注：

- [ ] 锁 key 是否过粗
- [ ] 是否可能死锁或永久占用
- [ ] 释放是否在 finally
- [ ] 锁内是否有远程调用

## 八、消息驱动

- 使用 RocketMQ 等可靠中间件；生产端与消费端约定消息键、重试次数、死信处理。
- 关键业务消息使用事务消息或本地消息表保证投递可靠。
- 消费端必须幂等；重复投递不得产生重复业务效果。
- 同一业务实体使用稳定消息键（如订单号），保证顺序与可追溯。
- 消费失败进入有限重试，超过阈值进入死信并提供补偿入口。

```text
topic: ORDER_EVENT
key: orderNo
tag: ORDER_CANCELLED
重试: 16 次（阶梯退避）
死信: %DLQ%order-consumer
```

## 九、可观测性

- 入口生成 traceId，贯穿 HTTP 调用、线程池与消息。
- 异步提交任务时包装上下文，消息头携带 traceId。
- 关键接口暴露指标：QPS、P50/P95/P99、错误率、线程池队列深度。
- 日志结构化，包含服务名、traceId、耗时、业务键。
- 对熔断打开、死信增长、补偿失败设置告警。

## 十、发布与容量

- 发布支持灰度：按用户标签、请求头或比例路由。
- 新版本先小流量观察错误率与延迟，再逐步放量。
- 服务支持优雅停机：先摘流量，处理完在途请求再退出。
- 方案必须给出容量估算、限流阈值与降级预案。
- 明确热点数据与缓存策略，避免缓存击穿打垮数据库。

## 方案评审清单

- [ ] 数据归属清晰，无共享库表
- [ ] 调用关系与失败路径画清楚
- [ ] 每个远程调用有超时
- [ ] 重试仅用于幂等操作
- [ ] 写接口与消费者有幂等策略
- [ ] 分布式事务选型有理由与补偿
- [ ] 锁粒度与释放安全
- [ ] 消息键、重试、死信明确
- [ ] traceId 与关键指标可观测
- [ ] 灰度、限流、降级、优雅停机具备
